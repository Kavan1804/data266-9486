Outputs/artifacts: Found and fixed a real gap in HW2.5.ipynb's Part D: the previous
  boundary-refinement logic only bisected when the required 512-16384 grid already
  contained both a success and a failure, which never happens on a 24 GB card since the
  whole grid succeeds trivially -- so the naive/fused OOM boundary (a required Table
  HW2.5.1 cell) would never actually be found. Replaced it with find_oom_boundary(), which
  extends the search geometrically (doubling from the largest grid success, up to 12 steps
  or a 120-second-per-probe time budget) until a failure appears, then bisects the bracket
  to a width of ~1024 (verified offline against a synthetic OOM threshold modeled on the
  classmate's actual ~85k-token failure point -- see Validation). Also broadened the OOM
  catch in Parts B, C, and D from `except torch.cuda.OutOfMemoryError` to a `RuntimeError`
  check on the message text, since OutOfMemoryError is only a RuntimeError subclass on
  newer PyTorch and older builds can raise a plain RuntimeError instead. Separately added a
  log_event() helper (writing to the new results/run_log_raw.txt) that auto-appends every
  Part A-E measurement as a UUID-labelled, timestamped line while the notebook runs, so
  reports/RUN_LOG.txt's STEP entries can be written from real saved data afterward instead
  of depending on manually copying values out of printed cell outputs.
Warnings/limitations: No GPU benchmark was executed at this step; the classmate's data was
  used only as a reference to design and validate the extension-search algorithm's
  parameters (step count, time budget, bisection granularity), not copied into this
